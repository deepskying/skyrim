# 0.9.7 法术身份与旧箭迁移

## 身份

现象：0.9.6 同法术、不同基材会占用不同 AMMO，但成品名称已隐藏基材。日志中的两批霜噬术各 7 支使用 C01/C02；旧日志没有基材字段，不能仅据日志确认两次基材相同。

新规则：以源 SpellItem 为唯一语义身份，制作数量、基材、炼金材料、玩家等级不参与匹配；同名但实际 Form 不同的法术不会混为一种。采用存档中持久的 AMMO/FLST 映射，不直接把名称或哈希写成 FormID，避免加载顺序变化和哈希冲突。物理基础伤害为 8，命中仍施放原法术。

新记录：AMMO 自身标记 + Spell + 既有 0xE00 STAT 主身份标记。源基材只作为本次交易耗材，不再保存。旧 FLST 的基材引用允许保留或缺失；多法术、多个基材、无 AMMO 标记、未知额外引用仍拒绝。所有原 ESP 记录和编号保持不变。

## 主身份选择

1. 优先使用已经保存主身份标记的活动记录。
2. 首次打开工坊迁移旧存档时，如果该法术已有旧箭正在装备，选择这组作为主身份；否则选槽位最早的一组。
3. 写入 STAT 标记并标记 FLST 的 kAddedForm 变化。以后换装备或读档仍使用此选择。
4. 所有旧槽位保留，永不用于别的法术。即使箭仍在随从、箱子或世界中，也不会被改绑。

在当前进程中通过已解析 Form 查询，跨存档加载由游戏的 Form 引用恢复，不保存易受插件加载顺序影响的裸 ID 字符串。

## 背包迁移

在已解除暂停、打开工坊并取得界面焦点之前执行，随后库存视图直接读取合并后的游戏库存。只替换玩家背包内属于同一法术的旧运行时别名，不扫描或修改世界所有容器/随从。取回旧箭后再次打开工坊会重新整理。

不强制卸下当前装备；不移除任务、附魔或带其他附加数据的物品。普通的 ExtraCount 可以合并，收藏、名称、所有权等数据不静默剥除。第一次迁移尽量以当前装备那组作目标，既保留装备又合并其他普通旧箭。

扣除后读取实际数量变化，完整扣除才添加目标；扣除不足恢复已扣部分，添加不足或添加抛出异常则恢复未送达部分。目标总量按 int 上限检查。这里是尽力恢复，不能承诺在任意第三方库存钩子拒绝恢复、进程崩溃或游戏异常时仍有数据库式原子性。

旧固定适配箭使用固定爆炸链，命中机制不同于运行时原法术施放，因此不自动跨机制转换。固定适配新制作统一使用该适配的第一个 AMMO、一次添加总产量，物理基础伤害也为 8。

## 验证

- arrow-identity-test：旧两槽迁移、装备优先仅首次生效、已保存主身份优先、失效与不同法术隔离；两种基材各 5 支但充能只够 7 支时合计产量正确；已有 7 支再添 7 支；总数溢出拒绝。
- 数量迁移：扣除/添加分别为 0、部分、全部；重复整理无重复添加；添加部分后抛出异常的余量恢复。
- runtime-rules-test：旧、新 FLST 结构解析，以及缺失法术、缺失基材、歧义引用的边界。
- native DLL 编译与发布包资源校验。
- 待实机：这两组霜噬术打开工坊后合并为 14 支；混合基材再做一批只增加数量；保存退出重进后再制作仍合并；旧箭交给随从和取回；装备高亮及命中效果。
